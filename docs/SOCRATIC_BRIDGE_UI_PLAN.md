# Implementation Plan: Socratic Bridge UI Integration 🧠🌉 (Actual Implementation & Rationale)

## 1. Executive Summary & Goals

The **Socratic Bridge** is the core pedagogical innovation of the News Decoder (GemmaLens) application. Rather than behaving as a passive AI rating service (System 1), the app uses Gemma to guide the user through critical reflection (System 2) about logical inconsistencies or rhetorical framing *before* showing final scores and fallacy deconstructions.

We have implemented a **Multi-Path Interstitial Screen Architecture**:
1.  **Objectivity Rating Path (Low-Friction)**: A 1–10 objectivity self-assessment. Users commit a rating and discuss the difference between their rating and the AI's objectivity score.
2.  **Stance Challenge Path (Core Belief)**: An "I Agree" vs. "I Disagree" binary stance selection. It challenges the user on their general stance, prompting a Socratic discussion on the merits, flaws, and how the evidence/arguments could be improved.
3.  **Structural Question Path (Deep-Dive / "Hard Mode")**: Exploring specific structural questions generated by Gemma.

### Goals Achieved
*   **Cognitive Commitment**: Prompt users to estimate objectivity or state their stance first, anchoring their prior beliefs before viewing the AI verdict.
*   **Low Barrier to Entry**: Make the initial action cognitively cheap (a simple slider or a binary stance tap) to encourage immediate engagement.
*   **Active Dialogue (Not Leading)**: Formulated the Socratic prompt so that it encourages critical thinking and guides the user to support their ideas, rather than telling them the AI's score upfront or answering the questions for them.
*   **Bypassing & History Exemptions**: Saved results from the library bypass the Socratic screen entirely. Hitting "Back" or the close button redirects directly to the main analysis report.

## 2. Navigation Flow & Back-Stack Contract

```
  Home Screen ──► [Loading/Thinking State]
                         │
                         ▼ (Pipeline Complete)
              [Socratic Challenge Screen]
               │                      │
               ├─► [Submit Rating] ───┼─► Classroom Chat (Pre-seeded with rating)
               │                      │
               ├─► [Select Stance] ───┼─► Classroom Chat (Pre-seeded with stance)
               │                      │
               ├─► [Select Question] ─┼─► Classroom Chat (Pre-seeded with question)
               │                      │
               └─► [Skip / Close [X]] ┼─► [Analysis Screen (Full Report)]
                                      │
                                      ▼ (Back / Done / View Report)
                                [Analysis Screen]
```

### Design Decisions on Navigation:
*   **Why we use Navigation Replacement (`navigator.replace(AnalysisScreen)`) before pushing `ChatScreen`**: 
    If a user enters a Socratic chat from the Socratic selection screen, we want the "Back" action or the "View Report" action to take them to the **AnalysisScreen** (detailed report) instead of dropping them back onto the Socratic question selector screen. By replacing the Socratic screen with the `AnalysisScreen` in the back-stack, we guarantee that clicking "Back" or "View Report" from the chat lands them on the final report screen, which is the logical next step.
*   **Historical Lookup**: Opening saved results from the Database directly calls `navigator.push(AnalysisScreen)`, bypassing the Socratic selection screen completely.

## 3. Data Passing & Persistence Strategy

To prevent memory leaks and circumvent the 8KB size limit of Android serialized arguments/bundles in Compose Navigation:
*   **No Raw String Passing**: Screens do not pass the article text or `AnalysisResult` data class in the screen constructor.
*   **State-Driven Screen Collections**: Both `ChatScreen` (rebranded to Classroom) and `AnalysisScreen` query the singleton `AnalysisCoordinator` (available via `ServiceRegistry.analysisCoordinator`) to collect the active state or read the analysis result.
*   **Shared SessionState & Persistence**:
    Added a lightweight `SocraticSession` data class inside `Models.kt` that is persisted to the local database:
    ```kotlin
    data class SocraticSession(
        val userObjectivityRating: Int? = null,
        val selectedQuestionIndex: Int? = null,
        val userStance: String? = null // "agree" or "disagree"
    )
    ```
    This enables user selections to survive application restarts and allows the analytical history tab to accurately display what engagement choice the user made.

## 4. UI Screen Layouts & Rebranding

### 4.1 `SocraticChallengeScreen.kt` (Rebranded to "Socratic Learning")
*   **Centered Header Title**: Rebranded the screen title to **Socratic Learning** for an educational, clean feel.
*   **Stance Challenge**:
    Added two highly visible container-colored buttons:
    *   **I Agree** (utilizing `MaterialTheme.colorScheme.primaryContainer` / `onPrimaryContainer` to convey agreement in a non-distracting, premium shade).
    *   **I Disagree** (utilizing `MaterialTheme.colorScheme.errorContainer` / `onErrorContainer` to convey disagreement).
*   **High-Contrast Action Button**: Replaced raw `Button` instances with `PrimaryButton` from our design system to ensure all text within primary buttons is rendered in white (`Color.White`), solving accessibility/readability issues against dark blue buttons.
*   **Loading State Polish**: Since Stage 5 (Socratic questions) runs asynchronously after Stage 1-4, users can arrive at the Socratic selection screen before questions are ready.
    *   We added a premium loader card ("Analyzing claims to formulate Socratic questions...") with a circular progress indicator.
    *   We resolved the state initialization bug where the fallback error message briefly flashed before the loading state was resolved.
    *   If a user clicks an action (like Stance or Slider) while the background analysis is still running, the screen displays a full-screen loading dialog and auto-navigates once the analysis completes.

### 4.2 `ChatScreen.kt` (Rebranded to "Classroom")
*   **Title**: Renamed the top bar title to **Classroom** to invoke a focused, conversational study environment.
*   **Prompt Tuning (Non-Leading Guide)**:
    Rather than stating the AI score immediately (which leads the user and defeats the Socratic purpose), the guide engages with the user's input constructively:
    *   *If Rating submitted*: Ask the user *why* they chose that rating, prompting them to explain their reasoning and then comparing it to structural findings.
    *   *If Stance submitted*: Challenge the user's choice. For agreement, prompt them on how they could strengthen the argument's evidence or where it relies too heavily on emotion. For disagreement, ask them to identify the key counter-argument or fallacy.
    *   *If Question submitted*: Guide the user to answer the question themselves, challenging their perspective, rather than feeding them an AI-generated answer.

## 5. Visual Aesthetics & Accessibility

*   **Color Theme**: Interactive components utilize harmonious HSL colors in dark and light modes.
*   **Responsive Scrolling**: Layout is wrapped in a `Column` with `verticalScroll`, and the action buttons are styled in a sticky column with `navigationBarsPadding` to ensure premium behavior across screen sizes and aspect ratios.
*   **Contrast Standards**: Primary buttons strictly use high-contrast white text, preventing low-contrast black text on blue backgrounds.
*   **Icons**: Consistent usage of accessible, simple vector icons (`Icons.Default.Close`, `Icons.Default.ArrowBack`, `Icons.Default.ArrowForward`).

## 6. Core Fixes & Enhancements (Parity & Lifecycle Stabilization)

To ensure the Socratic Bridge is production-grade and completely robust:

### 6.1 Audio Analysis Pipeline Parity
*   **Parity in `AnalysisCoordinator.kt`**: Integrated Socratic Bridge questions into the audio analysis pipeline as Stage 5, right after Vocal Tone synthesis and before Fallacies scan.
*   **Pre-Priming Context**: Prime the LiteRT inference engine with the merged transcript and observations before triggering stages, allowing subsequent chat responses to have the appropriate context.

### 6.2 Lifecycle & Navigation Stability
*   **Single-Navigation Protection**: Added a `rememberSaveable` flag (`socraticNavigated`) to `AnalysisScreen.kt` to ensure the screen replacement only fires once upon the first time the inference completes, preventing multiple stacked replacements on progressive stage updates.
*   **Unified Pending Navigation**: Replaced the separate pending navigation variables with a unified `PendingNavigation` sealed interface and saved it using a custom list saver (`PendingNavigationSaver`). This prevents state loss on configuration changes and guarantees the user's intent is carried through if the analysis completes while they wait.
*   **Removal of Dead `initialMessage`**: Cleaned up the `initialMessage` constructor argument from the Socratic navigation transitions, relying entirely on the orchestrator session context.
*   **Clean Socratic Prompting**: Replaced "SYSTEM:" instruct prefixes with natural assistant-guided prompt instructions in `ChatScreen.kt` to prevent instructions from leaking into the user role context.
*   **Re-engagement Classroom Card**: Added a custom `Socratic Learning` re-engagement card to the bottom of the analytical report in `AnalysisScreen.kt` so users can enter the classroom chat even after dismissing the initial challenge flow.
